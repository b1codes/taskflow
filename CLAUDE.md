# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Taskflow is a Go CLI + MCP server that connects local coding sessions to ClickUp tasks: it tracks session start/checkpoint/stop lifecycle, captures git context, and asynchronously syncs progress comments and status updates back to ClickUp. It exposes the same functionality two ways — as Cobra CLI commands (`./taskflow start ...`) and as MCP tools (`tf_start`, `tf_checkpoint`, etc.) served over stdio for LLM agent integration.

## Commands

```bash
go build ./cmd/taskflow       # build the binary (outputs ./taskflow)
go test ./...                 # run all tests
go test ./internal/session/... -run TestName   # run a single test
go vet ./...
```

There is no Makefile or CI config in this repo — the above `go` commands are the only build/test tooling.

Running the built binary:
```bash
./taskflow init                # scan ClickUp workspace, populate local cache
./taskflow start <task_id> <project_path>
./taskflow checkpoint <session_id> --summary "summary" --files a.go,b.go
./taskflow decision <session_id> --topic "..." --decision "..." --rationale "..."
./taskflow snag <session_id> --error "error text" --category build
./taskflow stop <session_id> --summary "..." --status completed [--force]   # --force overrides the block gate (CLI only)
./taskflow list --status active,paused
./taskflow completeness <session_id>   # obligations owed under the project's completeness manifest
./taskflow waive <session_id> <obligation_id> --rationale "..."   # logged as a decision
./taskflow attest <session_id> <obligation_id> --evidence "..."
./taskflow plan <session_id> --rule react-screen --var feature=payments --var name=CheckoutPage   # or --decline "reason"
./taskflow verify <session_id>         # run command checks now (needs [completeness] allow_commands = true)
./taskflow check [--session ID | --project PATH] [--hook claude]   # exit 2 while required obligations are open
./taskflow completeness report [--project PATH] [--since 30d] [--format text|json|b1]   # drift report
./taskflow serve                # run as MCP server over stdio
./taskflow sync                 # manually drain the sync queue once, then prune finished ops
```

Config lives at `~/.taskflow/config.toml` (auto-created on first run with defaults from `internal/config/config.go`'s `DefaultConfigContent`). `CLICKUP_API_KEY` env var overrides the config file's key. The SQLite DB path defaults to `~/.taskflow/sessions.db`.

## Architecture

Layered dependency flow: `cli` and `server` are two thin front-ends over the same `session.Service`, which is the sole orchestrator of business logic. Neither front-end talks to `store` or `clickup` directly except to construct and inject dependencies.

- **`internal/session`** — the core. `Service` (service.go) implements Start/Checkpoint/LogSnag/List/Stop against the `SessionStore` interface (defined here, implemented by `store`). It depends on small interfaces it also defines — `ClickUpClient`, `GitCapturer`, and the optional `CompletenessEvaluator` (set via `WithCompleteness`) — implemented by shared adapters in `internal/adapters` wrapping `internal/clickup`, `internal/gitctx`, and `internal/completeness`. This inversion means `session` has zero import of `clickup` or `gitctx` packages directly; check `service.go`'s interfaces before adding new external calls.
- **`internal/adapters`** — shared implementations of `session.GitCapturer` (`GitCapturer` wrapping `internal/gitctx`), `session.ClickUpClient` (`ClickUpAdapter` wrapping `internal/clickup`), and `session.CompletenessEvaluator` (`CompletenessEvaluator` joining `internal/completeness` with `gitctx.ChangedSince`; its `HasManifest` stats `completeness.ManifestPaths` without evaluating). Used by both `cli` (via `newSessionService`) and `server` to construct `session.Service`, with `WithCommands(cfg.Completeness.AllowCommands, CommandTimeout())`. `RunCommands` (command.go) is the only place taskflow executes project commands: `/bin/sh -c` in the stack root, stack `env` appended over `os.Environ()` minus taskflow's own credentials (`inheritedEnvDenylist`: `CLICKUP_API_KEY`; a stack `env:` may still set them), stdin closed, output written to a pipe of its own (so `Wait` returns when the shell exits) and kept by `tailBuffer` as its last 8 KiB, its process group killed on timeout and again once the shell exits (`killGroup`, `command_unix.go`; non-unix fails the check), so nothing it left in the background leaks or holds the output open: a shell that exits 0 passes. `RunCommands` hashes the work tree before and after its batch (`snapshot`/`stamp`) and stamps each `CommandCheck.Fingerprint` with the after-state plus the spec's env when `gitctx.WorkTreeState.Content` didn't change, so ignored files the run wrote (logs, coverage, caches) count as its own output; when content changed during the run (or the after-hash failed) it stamps the pre-run state, so the pass is stale. Every failure is a failed `CommandCheck`, never an error.
- **`internal/completeness`** — pure (reads project files only; the changed set is passed in; executes nothing): loads and validates the manifest (`.agents/completeness.yaml`, else `.taskflow/completeness.yaml`, strict YAML so typos fail loudly), compiles `{var}`/`*`/`**` path patterns, resolves stack vars and commands from conditions plus `.agents/project/completeness.yaml` overrides (nothing is executed), and turns changes into `Finding`s. `session/completeness.go` owns the obligation types and `mergeObligations`: new keys insert, `waived`/`attested` are sticky (for obligations that originated in the session), `open` ⇄ `satisfied` recompute, missing keys void — except when the evaluation is `Partial` (no git, dirty-files-only fallback, 500-file cap), which keeps what it didn't find; a `Partial` evaluation also re-verifies stored open/satisfied obligations (`completeness.Recheck`) so work finished outside the partial change set is noticed. Inherited obligations a full evaluation doesn't find are voided whatever their status (their file is gone). Rechecks the manifest no longer allows (rule removed/renamed, stack missing, subject outside the stack root or no longer matching the rule) come back as `completeness.Result.Dropped` → `Evaluation.Dropped`, with a warning, and void their obligations in any status, planned included, even when `Partial`. An invalid manifest voids nothing. `mergeObligations` is pure; `mergeEvaluation` merges in memory and `persistMerge` writes it (`writeMerge`, returning joined write errors) then queues the checklist, with `applyEvaluation` = both, logging failures. `tf_completeness` on a non-active session reports stored obligations without evaluating. `deleted:` triggers fire on a `D` change or a rename's `OldPath` (`Rule.fire`); `relativeTo` turns a rename across a stack root's edge into an add (old path cleared) or a delete; an undeclared recheck applies while its file is as its trigger found it (present for added/modified/changed, gone for deleted: `matchPath(rel, deleted)`); `absent:` passes when nothing matches, and shows in `Expected` as `must not exist: <path>` (`AbsentPrefix`), never as a bare path.
  Command checks: `EvaluateWith(…, Options{Commands})` puts a `CommandSpec` (line, stack root, env) on a finding whose `run:` resolves, and then `attest_when: no_command` asks no attestation; `Finding.Satisfied`/`ChecksPassed` stay structural. In `session`, `runCommandChecks` (only from `evaluateUnsaved(…, run=true)`: `Verify` and `Stop(completed)`, never checkpoints) runs each distinct (root, line, env) once (`runKey`; `envKey` is a sha256 of the sorted env, recorded as the check's `env`), skipping waived obligations, and sets `CompletenessFinding.CommandResult` by spec before the merge; `evaluateUnsaved` then re-reads the obligations and merges against that read, so a waive or attest made while commands ran isn't overwritten (a failed re-read counts as unchecked); `withCommand` then requires a pass of the same line, root, and env: this run's, or the obligation's stored `CommandCheck` (migration 8, `command_check` JSON; an upsert with none keeps the stored one) only while it is `current` — its `Fingerprint` non-empty and equal to the spec's. The adapter fingerprints a spec only when a stored obligation has a passing, fingerprinted `CommandCheck` for the same root and line (or the changed set couldn't be read), else leaves it "", as sha256 of `gitctx.WorkTreeHash` (the whole repository, not the stack root, since tests read shared code: the git tree the content would commit as, staged into a temporary copy of the index that keeps the real index's mtime for racy-git, with assume-unchanged/skip-worktree cleared and fsmonitor/untracked cache off, so the real index is never touched; plus ignored files and top-level ignored dirs by path/size/mtime and initialized submodules recursively; commit-independent; any failure is an error) plus the sorted env, "" without git (with a warning). `runCommandChecks` keeps the fingerprint the runner stamped, falling back to the spec's when it is empty. So a pass goes stale after any change other than ignored files its own run wrote (an ignored file anyone changes during the run counts as the run's; a suite that writes non-ignored output differs every run, so gitignore it) (views say "stale: …"), and `Check`/checkpoints can't pass on an old result; it adds the `command` level, and a failure reopens. A blocked stop discards its runs like the rest of its evaluation (the error's views carry the output). `Attest` refuses a command-checked finding with `ErrNotAttestable` pointing at `tf_verify`. `Verify` (`tf_verify`/`taskflow verify`) needs `Evaluation.CommandsEnabled` (`ErrCommandsDisabled`), and returns an error naming the runs when their results can't be recorded (they don't count). `Check` (`taskflow check`) evaluates and merges without running commands; it blocks only an active session, and treats an unchecked evaluation as blocked; `--hook claude` reads the Stop-hook stdin (`stop_hook_active` → exit 0 silently; `cwd` stands in for `--project`) and prints `{"decision":"block","reason":…}` with exit 0; in hook mode every failure (config load, held by check's own `PersistentPreRunE`; lock read; database; evaluation; unreadable or invalid hook input; bad flags; an unknown `--session`) is answered with a block naming the error and exit 0, never exit 1, which Claude Code would let the agent stop on, while `stop_hook_active` and nothing to check (no lock, a locked session the DB doesn't know, an inactive session, no manifest) exit 0 silently; otherwise a block exits 2 via `cli.ExitError`, which `Execute` maps to the exit status. The ClickUp "Taskflow · Definition of Done" checklist (`session/checklist.go`) is queued as a `SYNC_CHECKLIST` op carrying the session's full desired checklist by `enqueueChecklist`, after every successful write (`persistMerge`, `Plan`, `Waive` — only while completeness is on, i.e. an evaluator is set and `CompletenessEvaluator.HasManifest` finds a manifest; the waiver itself is always recorded — and `Attest`, which writes its evaluation with `writeMerge` and queues once with its final state): it queues when the payload's items differ from the task's latest `SYNC_CHECKLIST` op (`LatestSyncOp`; `sameChecklist` compares by `Key`, whatever the order), that op failed for good or applied only in part (`PARTIAL`), there is none and the session has obligations, or the latest op can't be read (a redundant op is harmless), so a checklist that drifted (an op out of retries, a session that predates the checklist) is repaired by the next evaluation. It queues through `enqueueSyncState` → `store.CoalesceSyncOp`: while the task's newest op is still waiting (pending, or failed with retries left) it takes the new payload and moves to the back of the queue instead of a second op being queued, so a stale op is never run, skipped, or retried ahead of the latest state. `Plan` writes its obligations and `plan_state` before queuing, so a plan that failed to record is never pushed. A failed write queues nothing, since the next evaluation sees the change again. Item names are `[requirement] describe (subject)` (the stable `Match` part, so one requirement on two files makes two items; the parenthetical is left out for the stackless subject `*`; whitespace normalized by `NormalizeChecklistName` as ClickUp stores it) plus a status suffix after ` — ` (`attested`/`waived`, one-word verify levels with ✓, or `void`); `ChecklistItemMatches` is the matching rule the worker uses and accepts only those suffixes (plus the legacy `~~match~~`), so an item whose describe is a prefix of another's doesn't take it over — keep it in step with `checklistItem`. Evaluation runs on `Start` (contract gets the full `completeness` section: gate, stacks, rules, summary, open, inherited, suggested_plan, protocol), `Checkpoint` (response gets `completeness`; comment gets a summary line), `Stop` (finished comment gets a table), and `tf_completeness`. `Service.WithCompleteness(nil)` or no manifest = feature off. A session's `base_sha` is recorded only when it is created, never on resume.
  Enforcement lives in `session/enforce.go`. `Waive` records a decision (`rejected_alternative`, posted to ClickUp) and links `waiver_decision_id`; `Attest` only accepts an obligation whose current finding carries an attest prompt (others get `ErrNotAttestable`: do the work or waive it — this is what keeps the block gate from being attested past), evaluates once, stores evidence, adds the `attest` level, and clears any `waiver_decision_id`; it refuses with `ErrCompletenessUnchecked` when completeness can't be checked. An attested obligation then moves attested ⇄ satisfied as its checks (`ChecksPassed`) pass or fail, never back to open, but only while its current finding still carries an attest prompt: once it doesn't (e.g. command checks were enabled), it goes open/satisfied by its checks like any other, the `attest` level is dropped, and its stored evidence is no longer shown (`standingEvidence`). `Plan` resolves items with `completeness.PlanSubject` (plannable rules only, a wildcard-free trigger, exact vars) and creates planned obligations plus a `subject-file` one for the file itself; it fails with `ErrInvalidPlan` when a planned subject yields no findings (e.g. its rule's stack isn't detected), and leaves `plan_state` unchanged when any obligation fails to save. Planned obligations are rechecked by subject (`Recheck.Declared`) even when the file isn't in the diff or doesn't exist yet; inherited ones are rechecked by subject only while the file exists. `plan_state` goes `none → suggested` (Start matched a rule's `plan_hints` against the task name or description as whole words; checkpoints then carry `plan_reminder`) `→ planned | declined`. A new session after a `COMPLETED`/`ARCHIVED` one inherits its open, attested, and waived obligations (`store.InheritObligations`) and its `plan_state` when `planned` or `declined`; a session that has planned obligations is never suggested a plan.
  The completion gate (`report | review | block`) is the stricter of `[completeness] gate` in config (default `review`) and the manifest's `gate:`: config is a floor the manifest (which the agent can edit) can't lower. Gate names are validated in one place, `session.ParseGateMode` (wrapped by `config.CompletenessConfig.GateMode()`; `server.New` returns an error for an invalid one), and an unknown `GateMode` ranks as `block`, so a bad value fails closed (`internal/completeness` keeps its own manifest check to stay free of a `session` import). When completeness can't be checked (invalid manifest, unreadable obligations, failed evaluation), the gate acts as if work may be open: `block` fails closed with `ErrCompletenessUnchecked`, `review` moves the task to review, `report` completes. It applies only to `Stop(completed)` with *required* obligations open: `review` enqueues `RoleReview` instead of `RoleComplete`, and `block` returns `*IncompleteSessionError` (`ErrIncompleteSession`) before anything is written — `Stop` merges the evaluation in memory (`evaluateUnsaved`) and persists it only once the gate lets the stop through, so a blocked stop writes no obligations or reminder counts (obligations it found first are listed as `Unrecorded`) — unless `force` is set (CLI `--force` only; records a decision). `Stop` returns `(*StopResult, error)`.
- **`internal/drift`** — the drift report over `store.DriftReport` rows (per source/rule/requirement: satisfied first vs after a reminder, attested, waived with rationales, open at stop vs in progress; void, inherited, and `subject-file` rows excluded; time filtered in Go since timestamps are stored as text with offsets): Jaccard clustering of waiver rationales, signals (`unfollowed`, `often-waived`, `reminder-dependent`, only with `MinSample` decided obligations), and `--format b1` suggestions aimed at `modules/<module>/context/` or `completeness.yaml` (or `.agents/project/…` without a source).
- **`internal/store`** — SQLite (via `modernc.org/sqlite`, no CGo) persistence. `Store` interface embeds `session.SessionStore` plus ClickUp cache and sync-queue methods. `migrations.go` holds a versioned, append-only list of SQL migrations run against a `schema_version` table on every `store.New()` — add new schema changes as a new entry in the `migrations` slice, never edit an existing one. WAL mode is set once per file by `enableWAL` (retrying `SQLITE_BUSY`), not as a DSN pragma: concurrent connections switching a fresh file to WAL fail without waiting on `busy_timeout`. A filesystem that can't do WAL (network mounts) keeps its rollback journal with a warning rather than failing `store.New`.
- **`internal/clickup`** — HTTP client for the ClickUp API (`client.go`), hierarchy discovery (`discovery.go`: workspace → space → folder → list → statuses), and `ScanWorkspace` (`scan.go`) which walks that hierarchy and caches it via `store`. `checklists.go` reads (`GetTaskChecklists`, from `GET /task/{id}`) and writes task checklists. `status.go`'s `ResolveStatusForRole` maps a lifecycle role (`start`/`reopen`/`complete`/`review`/`archive`, sent by `session.Service` as the `UPDATE_STATUS` payload `{"role": …}`; `Start` sends `reopen` when the task's live ClickUp status is `done`/`closed`) to a status on the task's list; `ApplyStatusRole` resolves and applies it. `ResolveTargetStatus`/`ApplyTargetStatus` (which the role functions wrap, so one resolver, cache refetch, and 400 retry serve both) also take the payload's `target_status`, from `tf_stop`'s `target_task_status` (`--target-task-status`; `Service.StopWithTaskStatus` takes one only on a completing stop, else `ErrTargetTaskStatus` before anything is written, and keeps it under the review gate): `resolveTarget` uses the list's status of that name (`_` read as a space), else a role alias (`review`/`completed`/`cancelled`…, `targetAliasRole`) resolved as that role with its `status_map` entry and no-status outcome; only `complete` may target a `done`/`closed` status or another role, so the review gate can't be named past; a target that can't be used warns and falls back to the role, whose own applies check then holds (an honored target only needs the task not `done`/`closed`, `checkTargetApplies`). The role constants live in `session` (`session.StatusRole`) and `clickup.StatusRole` is a type alias, so both sides share them. ClickUp status types are only `open`/`custom`/`done`/`closed` — never `active` — so roles resolve by type + orderindex + whole-word name matching, with optional `[clickup.status_map]` overrides; `complete` prefers `done` before `closed` (matching `complete`/`completed`/`done` hints first), excludes cancel/archive names (`archivePrefixes`), and never picks a `custom` status (reopen couldn't move the task back out of it); `archive` only targets a cancel-like closed status, never a plain "complete"; `review` only targets a `custom` status with the whole word "review", else no change. It fetches the task live and returns `ErrSkipStatusChange` when the role doesn't apply to the task's current status (`start` only from `open`; `reopen` from `open`/`done`/`closed`; `complete`/`archive` never from `done`/`closed`; `review` also never from a custom review/QA stage like `in review`/`testing/qa`, `reviewStagePrefixes`), so taskflow never undoes a status someone else set. `complete` does finish a task from review (taskflow's own review gate puts it there); an agent that moved the task to review for an open PR stops with `status="in_review"` (`normalizeStopTarget`: completes the session with `RoleReview`) instead. Statuses are cached per list (key `<list_id>/<name>`, replaced atomically via `store.ReplaceListStatuses`) with a 24h staleness check; the cache is also refetched when the task's live status isn't in it, when an override misses (a confirmed miss is trusted for 10 minutes), or when ClickUp rejects a cached name with a 400 (then the update is retried once if the refreshed list resolves to a different name; a final rejection wraps `ErrStatusRejected`).
- **`internal/sync`** — `Worker` drains `sync_queue` rows written by `session.Service.enqueueSync`. Two modes: `Run` (ticker-driven background loop, started as a goroutine by `cli/serve.go` alongside the MCP server so checkpoints/stops are automatically synced to ClickUp) and `DrainOnce` (single pass, used by `taskflow sync`). An op is claimed atomically by `store.MarkInFlight`, which returns the row as claimed (a payload coalesced after the op was listed is the one applied; an op another worker claimed is left alone). Failed ops are retried up to `max_retries`, except errors that can't succeed on retry (`isPermanent`: unknown role/operation, no matching status, a 400 to the op's own write — the comment POST or the final status update — but not to a lookup along the way), which go straight to `MarkFailedPermanent`. `SYNC_CHECKLIST` (`syncChecklist`) reconciles the task's checklist with the op's full desired state: find it by name or create it, match items by exact name when every wanted item has one, or when only void items are unmatched and no ClickUp item is left over (nothing changes, no history read); otherwise first by the stable parts each obligation `Key` had in the task's earlier applied (`DONE`/`PARTIAL`) `SYNC_CHECKLIST` payloads (`store.ListSyncHistory`, last `store.MaxSyncHistory` = 50; a skipped, failed, or waiting op may have written nothing), one recency rank at a time across Keys, then by name, then by the current stable `[requirement] describe (subject)` part. History goes first because it is the only evidence of whose an item is, so a new Key rendering an edited Key's old text can't take its item, an edited describe renames its item instead of duplicating it, and items named before the subject was added are still found; names are compared normalized. Create missing items (never void ones; a created item is identified by the ID new in ClickUp's response, re-reading the checklist if the response omits it, then by name or stable part; one that still can't be identified is left unresolved and the op marked `PARTIAL` via `store.MarkPartial` — never an error, since an immediate retry could create it again — so the next evaluation queues the checklist again and finds it by name) and rename/(un)resolve the rest; items are never deleted, so no ClickUp IDs are stored. Since ops are coalesced, a newer op only exists beside a waiting one when it was queued while the older was in flight; for that case an op is skipped (marked `SKIPPED` via `store.MarkSkipped`, distinct from `DONE`, and not counted as synced) when `store.HasNewerOp` finds a later one for the same task that applied (in the sync history) or still will (pending, in flight, or failed with retries left), so a retried stale op never undoes a newer state; a `SKIPPED` or permanently failed later op doesn't count. A 400 to one item's create or update skips only that item: the rest are applied and the op is `DONE` with the rejected items in its `error_msg` (`store.MarkDone`'s note), since the same payload would be rejected again. A 400 to creating the checklist is permanent; a 400 to the lookup is retried. Finished ops are pruned by `Worker.Prune` (in `Run` on its first idle pass and then daily, also without a ClickUp client; after `taskflow sync`, where a prune failure only warns) via `store.PruneSyncQueue`: rows whose `finished_at` (unix seconds, set by `MarkDone`/`MarkPartial`/`MarkSkipped`/`MarkFailedPermanent` and by `MarkFailed` once retries run out; migration 9 backfilled it) is more than `[sync] retention_days` ago (default 30, at most `config.MaxRetentionDays`, 0 keeps them forever) are deleted by one indexed `DELETE`; waiting and in-flight rows have none and are never touched. Nothing that reads old rows depends on the queue: applied `SYNC_CHECKLIST` ops are copied, in the same transaction as their `DONE`/`PARTIAL` mark, to `sync_history` (each task's newest `MaxSyncHistory`), which item matching, `HasNewerOp`, and `LatestSyncOp` (the queue's row first, the history's once it's pruned) read. The waiting-op condition is spelled once, as `waitingSyncOp`/`retryableSyncOp` in `store/sqlite.go`. `SyncConfig.RateLimitMS` is enforced per HTTP request by `clickup.Client.WithMinInterval`; a 429's `Retry-After` holds back every request on the client. `serve` shares one paced client between the MCP tools and the worker.
- **`internal/gitctx`** — captures branch/SHA/dirty-files for a project path; used by `internal/adapters.GitCapturer`. `ChangedSince` (changes.go) lists files changed since a base commit (`git diff --name-status -M --relative` plus `ls-files --others`), falling back to the merge-base with `.agents/config.yaml`'s `default_branch` (else `main`) when the base is missing or no longer an ancestor of HEAD, then to uncommitted changes only (`Partial`, also when that merge-base is HEAD itself). Files changed only by merges on HEAD's first-parent line (main merged into the branch) are dropped. `HashWorkTree` (worktree.go) fingerprints the repository's working tree for command-check passes as `WorkTreeState{Content, Ignored}` (the git tree of tracked and untracked content, and the ignored entries by path/size/mtime, each including submodules); `WorkTreeHash` is their combination (`WorkTreeState.Hash`).
- **`internal/cli`** — one file per Cobra subcommand, registered via `init()` on the package-level `rootCmd` in `root.go`. `PersistentPreRunE` on root loads config into the command context (`ConfigFromContext`); every subcommand opens its own `store.New(cfg.DBPath())` and closes it via `defer`.
- **`internal/server`** — MCP server (`mark3labs/mcp-go`). `registerTools()` maps each `tf_*` tool to a handler that parses MCP args and calls into the same `session.Service` methods the CLI uses with shared adapters from `internal/adapters`.

### Session state machine

Status values: `ACTIVE`, `PAUSED`, `COMPLETED`, `ARCHIVED` (`internal/session/status.go`). Transitions are validated by `ValidateTransition`: `ACTIVE` and `PAUSED` can go anywhere; `COMPLETED` can only move to `COMPLETED` or `ARCHIVED`; `ARCHIVED` is terminal. `Service.Start` treats an existing `PAUSED` session for the same task as a resume (reuses session ID); `COMPLETED`/`ARCHIVED` sessions cause a new session to be created instead.

### Locking

A per-project advisory lock lives at `<project_path>/.b1codes/session.lock` (`internal/session/lock.go`), containing the active session ID. `Service.Start` refuses to start a *different* task in a project that already has an active session locked, unless the existing session isn't actually `ACTIVE` anymore.

### Agentic contract

`Service.BuildAgenticContract` assembles the JSON payload returned by `tf_start`/CLI `start` — recent checkpoints, logged decisions & dialogue rationales, unresolved snags, and cross-session "related resolutions" (snags with a matching normalized error signature resolved in *other* sessions/projects, found via `store.FindMatchingResolutions`). This is the primary mechanism for giving an LLM agent continuity across session starts/resumes.
