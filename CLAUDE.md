# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Taskflow is a Go CLI + MCP server that connects local coding sessions to ClickUp tasks: it tracks session start/checkpoint/stop lifecycle, captures git context, and asynchronously syncs progress comments and status updates back to ClickUp. It exposes the same functionality two ways — as Cobra CLI commands (`./taskflow start ...`) and as MCP tools (`tf_start`, `tf_checkpoint`, etc.) served over stdio for LLM agent integration.

## Commands

```bash
go build ./cmd/taskflow       # build the binary (outputs ./taskflow)
go test ./...                 # run all tests
go test ./internal/session/... -run TestName   # run a single test
go vet ./...
```

There is no Makefile or CI config in this repo — the above `go` commands are the only build/test tooling.

Running the built binary:
```bash
./taskflow init                # scan ClickUp workspace, populate local cache
./taskflow start <task_id> <project_path>
./taskflow checkpoint <session_id> --summary "summary" --files a.go,b.go
./taskflow decision <session_id> --topic "..." --decision "..." --rationale "..."
./taskflow snag <session_id> --error "error text" --category build
./taskflow stop <session_id> --summary "..." --status completed [--force]   # --force overrides the block gate (CLI only)
./taskflow list --status active,paused
./taskflow completeness <session_id>   # obligations owed under the project's completeness manifest
./taskflow waive <session_id> <obligation_id> --rationale "..."   # logged as a decision
./taskflow attest <session_id> <obligation_id> --evidence "..."
./taskflow plan <session_id> --rule react-screen --var feature=payments --var name=CheckoutPage   # or --decline "reason"
./taskflow serve                # run as MCP server over stdio
./taskflow sync                 # manually drain the sync queue once
```

Config lives at `~/.taskflow/config.toml` (auto-created on first run with defaults from `internal/config/config.go`'s `DefaultConfigContent`). `CLICKUP_API_KEY` env var overrides the config file's key. The SQLite DB path defaults to `~/.taskflow/sessions.db`.

## Architecture

Layered dependency flow: `cli` and `server` are two thin front-ends over the same `session.Service`, which is the sole orchestrator of business logic. Neither front-end talks to `store` or `clickup` directly except to construct and inject dependencies.

- **`internal/session`** — the core. `Service` (service.go) implements Start/Checkpoint/LogSnag/List/Stop against the `SessionStore` interface (defined here, implemented by `store`). It depends on small interfaces it also defines — `ClickUpClient`, `GitCapturer`, and the optional `CompletenessEvaluator` (set via `WithCompleteness`) — implemented by shared adapters in `internal/adapters` wrapping `internal/clickup`, `internal/gitctx`, and `internal/completeness`. This inversion means `session` has zero import of `clickup` or `gitctx` packages directly; check `service.go`'s interfaces before adding new external calls.
- **`internal/adapters`** — shared implementations of `session.GitCapturer` (`GitCapturer` wrapping `internal/gitctx`), `session.ClickUpClient` (`ClickUpAdapter` wrapping `internal/clickup`), and `session.CompletenessEvaluator` (`CompletenessEvaluator` joining `internal/completeness` with `gitctx.ChangedSince`; its `HasManifest` stats `completeness.ManifestPaths` without evaluating). Used by both `cli` (via `newSessionService`) and `server` to construct `session.Service`.
- **`internal/completeness`** — pure (reads project files only; the changed set is passed in): loads and validates the manifest (`.agents/completeness.yaml`, else `.taskflow/completeness.yaml`, strict YAML so typos fail loudly), compiles `{var}`/`*`/`**` path patterns, resolves stack vars and commands from conditions plus `.agents/project/completeness.yaml` overrides (nothing is executed), and turns changes into `Finding`s. `session/completeness.go` owns the obligation types and `mergeObligations`: new keys insert, `waived`/`attested` are sticky (for obligations that originated in the session), `open` ⇄ `satisfied` recompute, missing keys void — except when the evaluation is `Partial` (no git, dirty-files-only fallback, 500-file cap), which keeps what it didn't find; a `Partial` evaluation also re-verifies stored open/satisfied obligations (`completeness.Recheck`) so work finished outside the partial change set is noticed. Inherited obligations a full evaluation doesn't find are voided whatever their status (their file is gone). Rechecks the manifest no longer allows (rule removed/renamed, stack missing, subject outside the stack root or no longer matching the rule) come back as `completeness.Result.Dropped` → `Evaluation.Dropped`, with a warning, and void their obligations in any status, planned included, even when `Partial`. An invalid manifest voids nothing. `mergeObligations` is pure; `mergeEvaluation` merges in memory and `persistMerge` writes it (`writeMerge`, returning joined write errors) then queues the checklist, with `applyEvaluation` = both, logging failures. `tf_completeness` on a non-active session reports stored obligations without evaluating. The ClickUp "Taskflow · Definition of Done" checklist (`session/checklist.go`) is queued as a `SYNC_CHECKLIST` op carrying the session's full desired checklist by `enqueueChecklist`, after every successful write (`persistMerge`, `Plan`, `Waive` — only while completeness is on, i.e. an evaluator is set and `CompletenessEvaluator.HasManifest` finds a manifest; the waiver itself is always recorded — and `Attest`, which writes its evaluation with `writeMerge` and queues once with its final state): it queues when the payload's items differ from the task's latest `SYNC_CHECKLIST` op (`LatestSyncOp`; `sameChecklist` compares by `Key`, whatever the order), that op failed for good, there is none and the session has obligations, or the latest op can't be read (a redundant op is harmless), so a checklist that drifted (an op out of retries, a session that predates the checklist) is repaired by the next evaluation. A failed write queues nothing, since the next evaluation sees the change again. Item names are `[requirement] describe (subject)` (the stable `Match` part, so one requirement on two files makes two items; the parenthetical is left out for the stackless subject `*`; whitespace normalized by `NormalizeChecklistName` as ClickUp stores it) plus a status suffix after ` — ` (`attested`/`waived`, one-word verify levels with ✓, or `void`); `ChecklistItemMatches` is the matching rule the worker uses and accepts only those suffixes (plus the legacy `~~match~~`), so an item whose describe is a prefix of another's doesn't take it over — keep it in step with `checklistItem`. Evaluation runs on `Start` (contract gets the full `completeness` section: gate, stacks, rules, summary, open, inherited, suggested_plan, protocol), `Checkpoint` (response gets `completeness`; comment gets a summary line), `Stop` (finished comment gets a table), and `tf_completeness`. `Service.WithCompleteness(nil)` or no manifest = feature off. A session's `base_sha` is recorded only when it is created, never on resume.
  Enforcement lives in `session/enforce.go`. `Waive` records a decision (`rejected_alternative`, posted to ClickUp) and links `waiver_decision_id`; `Attest` only accepts an obligation whose current finding carries an attest prompt (others get `ErrNotAttestable`: do the work or waive it — this is what keeps the block gate from being attested past), evaluates once, stores evidence, adds the `attest` level, and clears any `waiver_decision_id`; it refuses with `ErrCompletenessUnchecked` when completeness can't be checked. An attested obligation then moves attested ⇄ satisfied as its checks (`ChecksPassed`) pass or fail, never back to open. `Plan` resolves items with `completeness.PlanSubject` (plannable rules only, a wildcard-free trigger, exact vars) and creates planned obligations plus a `subject-file` one for the file itself; it fails with `ErrInvalidPlan` when a planned subject yields no findings (e.g. its rule's stack isn't detected), and leaves `plan_state` unchanged when any obligation fails to save. Planned obligations are rechecked by subject (`Recheck.Declared`) even when the file isn't in the diff or doesn't exist yet; inherited ones are rechecked by subject only while the file exists. `plan_state` goes `none → suggested` (Start matched a rule's `plan_hints` against the task name or description as whole words; checkpoints then carry `plan_reminder`) `→ planned | declined`. A new session after a `COMPLETED`/`ARCHIVED` one inherits its open, attested, and waived obligations (`store.InheritObligations`) and its `plan_state` when `planned` or `declined`; a session that has planned obligations is never suggested a plan.
  The completion gate (`report | review | block`) is the stricter of `[completeness] gate` in config (default `review`) and the manifest's `gate:`: config is a floor the manifest (which the agent can edit) can't lower. Gate names are validated in one place, `session.ParseGateMode` (wrapped by `config.CompletenessConfig.GateMode()`; `server.New` returns an error for an invalid one), and an unknown `GateMode` ranks as `block`, so a bad value fails closed (`internal/completeness` keeps its own manifest check to stay free of a `session` import). When completeness can't be checked (invalid manifest, unreadable obligations, failed evaluation), the gate acts as if work may be open: `block` fails closed with `ErrCompletenessUnchecked`, `review` moves the task to review, `report` completes. It applies only to `Stop(completed)` with *required* obligations open: `review` enqueues `RoleReview` instead of `RoleComplete`, and `block` returns `*IncompleteSessionError` (`ErrIncompleteSession`) before anything is written — `Stop` merges the evaluation in memory (`evaluateUnsaved`) and persists it only once the gate lets the stop through, so a blocked stop writes no obligations or reminder counts (obligations it found first are listed as `Unrecorded`) — unless `force` is set (CLI `--force` only; records a decision). `Stop` returns `(*StopResult, error)`.
- **`internal/store`** — SQLite (via `modernc.org/sqlite`, no CGo) persistence. `Store` interface embeds `session.SessionStore` plus ClickUp cache and sync-queue methods. `migrations.go` holds a versioned, append-only list of SQL migrations run against a `schema_version` table on every `store.New()` — add new schema changes as a new entry in the `migrations` slice, never edit an existing one. WAL mode is set once per file by `enableWAL` (retrying `SQLITE_BUSY`), not as a DSN pragma: concurrent connections switching a fresh file to WAL fail without waiting on `busy_timeout`.
- **`internal/clickup`** — HTTP client for the ClickUp API (`client.go`), hierarchy discovery (`discovery.go`: workspace → space → folder → list → statuses), and `ScanWorkspace` (`scan.go`) which walks that hierarchy and caches it via `store`. `checklists.go` reads (`GetTaskChecklists`, from `GET /task/{id}`) and writes task checklists. `status.go`'s `ResolveStatusForRole` maps a lifecycle role (`start`/`reopen`/`complete`/`review`/`archive`, sent by `session.Service` as the `UPDATE_STATUS` payload `{"role": …}`; `Start` sends `reopen` when the task's live ClickUp status is `done`/`closed`) to a status on the task's list; `ApplyStatusRole` resolves and applies it. The role constants live in `session` (`session.StatusRole`) and `clickup.StatusRole` is a type alias, so both sides share them. ClickUp status types are only `open`/`custom`/`done`/`closed` — never `active` — so roles resolve by type + orderindex + whole-word name matching, with optional `[clickup.status_map]` overrides; `archive` only targets a cancel-like closed status, never a plain "complete"; `review` only targets a `custom` status with the whole word "review", else no change. It fetches the task live and returns `ErrSkipStatusChange` when the role doesn't apply to the task's current status (`start` only from `open`; `reopen` from `open`/`done`/`closed`; `complete`/`review`/`archive` never from `done`/`closed`), so taskflow never undoes a status someone else set. Statuses are cached per list (key `<list_id>/<name>`, replaced atomically via `store.ReplaceListStatuses`) with a 24h staleness check; the cache is also refetched when the task's live status isn't in it, when an override misses (a confirmed miss is trusted for 10 minutes), or when ClickUp rejects a cached name with a 400 (then the update is retried once if the refreshed list resolves to a different name; a final rejection wraps `ErrStatusRejected`).
- **`internal/sync`** — `Worker` drains `sync_queue` rows written by `session.Service.enqueueSync`. Two modes: `Run` (ticker-driven background loop, started as a goroutine by `cli/serve.go` alongside the MCP server so checkpoints/stops are automatically synced to ClickUp) and `DrainOnce` (single pass, used by `taskflow sync`). Failed ops are retried up to `max_retries`, except errors that can't succeed on retry (`isPermanent`: unknown role/operation, no matching status, a 400 to the op's own write — the comment POST or the final status update — but not to a lookup along the way), which go straight to `MarkFailedPermanent`. `SYNC_CHECKLIST` (`syncChecklist`) reconciles the task's checklist with the op's full desired state: find it by name or create it, match items by exact name when every wanted item has one (nothing changes, no history read); otherwise first by the stable parts each obligation `Key` had in the task's earlier non-`SKIPPED` `SYNC_CHECKLIST` payloads (`store.ListSyncOps`, last 50), one recency rank at a time across Keys, then by name, then by the current stable `[requirement] describe (subject)` part. History goes first because it is the only evidence of whose an item is, so a new Key rendering an edited Key's old text can't take its item, an edited describe renames its item instead of duplicating it, and items named before the subject was added are still found; names are compared normalized. Create missing items (never void ones; a created item is identified by the ID new in ClickUp's response, re-reading the checklist if the response omits it, then by name or stable part; one that still can't be identified is left unresolved with a warning, never an error, since a retry would create it again) and rename/(un)resolve the rest; items are never deleted, so no ClickUp IDs are stored. An op is skipped (marked `SKIPPED` via `store.MarkSkipped`, distinct from `DONE`) when `store.HasNewerOp` finds a later one for the same task that applied (`DONE`) or still will (pending, in flight, or failed with retries left), so a retried stale op never undoes a newer state; a `SKIPPED` or permanently failed later op doesn't count, so if the op it was skipped for fails for good an older op still applies its own state rather than leaving the checklist stale. A 400 to one of its writes is permanent; a 400 to the lookup is retried. `SyncConfig.RateLimitMS` is enforced per HTTP request by `clickup.Client.WithMinInterval`; a 429's `Retry-After` holds back every request on the client. `serve` shares one paced client between the MCP tools and the worker.
- **`internal/gitctx`** — captures branch/SHA/dirty-files for a project path; used by `internal/adapters.GitCapturer`. `ChangedSince` (changes.go) lists files changed since a base commit (`git diff --name-status -M --relative` plus `ls-files --others`), falling back to the merge-base with `.agents/config.yaml`'s `default_branch` (else `main`) when the base is missing or no longer an ancestor of HEAD, then to uncommitted changes only (`Partial`, also when that merge-base is HEAD itself). Files changed only by merges on HEAD's first-parent line (main merged into the branch) are dropped.
- **`internal/cli`** — one file per Cobra subcommand, registered via `init()` on the package-level `rootCmd` in `root.go`. `PersistentPreRunE` on root loads config into the command context (`ConfigFromContext`); every subcommand opens its own `store.New(cfg.DBPath())` and closes it via `defer`.
- **`internal/server`** — MCP server (`mark3labs/mcp-go`). `registerTools()` maps each `tf_*` tool to a handler that parses MCP args and calls into the same `session.Service` methods the CLI uses with shared adapters from `internal/adapters`.

### Session state machine

Status values: `ACTIVE`, `PAUSED`, `COMPLETED`, `ARCHIVED` (`internal/session/status.go`). Transitions are validated by `ValidateTransition`: `ACTIVE` and `PAUSED` can go anywhere; `COMPLETED` can only move to `COMPLETED` or `ARCHIVED`; `ARCHIVED` is terminal. `Service.Start` treats an existing `PAUSED` session for the same task as a resume (reuses session ID); `COMPLETED`/`ARCHIVED` sessions cause a new session to be created instead.

### Locking

A per-project advisory lock lives at `<project_path>/.b1codes/session.lock` (`internal/session/lock.go`), containing the active session ID. `Service.Start` refuses to start a *different* task in a project that already has an active session locked, unless the existing session isn't actually `ACTIVE` anymore.

### Agentic contract

`Service.BuildAgenticContract` assembles the JSON payload returned by `tf_start`/CLI `start` — recent checkpoints, logged decisions & dialogue rationales, unresolved snags, and cross-session "related resolutions" (snags with a matching normalized error signature resolved in *other* sessions/projects, found via `store.FindMatchingResolutions`). This is the primary mechanism for giving an LLM agent continuity across session starts/resumes.
